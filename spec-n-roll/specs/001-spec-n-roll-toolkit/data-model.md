# Data Model: Spec-n-Roll Toolkit

## Agent Configuration

Represents a developer-selected AI coding agent and the files generated for that agent.

**Fields**:

- `id`: Stable agent identifier (kebab-case product slug, no vendor prefix), e.g. `cursor`, `claude-code`, `copilot`, `codex`
- `displayName`: Human-readable agent name
- `enabled`: Whether this project currently generates and exposes workflow commands for the agent
- `ruleTargets`: Agent-specific rules/config files generated by the toolkit
- `skillTargets`: Agent-specific skill/command files generated by the toolkit
- `mcpConfigTargets`: Project-relative paths to native MCP configuration files (from extension manifest `agentSetup.mcpConfig.targets`)
- `mcpServerId`: Stable merge key for the Spec-N-Roll MCP server entry (from extension manifest `agentSetup.mcpConfig.serverId`, e.g. `spec-n-roll`)
- `mcpBinaryPath`: Resolved path to `.spec-n-roll/cli/bin/spec-n-roll-mcp` (+ `.cmd` on Windows when applicable)
- `commandPrefix`: Must be `spec-n-`

**Validation**:

- Bundled OOTB extension `id` values are `cursor`, `claude-code`, `copilot`, and `codex` — each MUST match the extension manifest `id`, bundled directory name, and `workflow.config.json` agent reference. `github-copilot` is not a valid extension `id` (use `displayName` for "GitHub Copilot" when needed).
- Selected agents are accepted as user input; the toolkit does not verify local installation.
- `init` and `config add-agent` create or idempotently update `mcpConfigTargets` to reference `mcpBinaryPath` via stdio transport.
- Merge upserts only the entry identified by `mcpServerId`; unrelated MCP server entries are preserved.
- `update` refreshes `mcpBinaryPath` in all enabled agents' `mcpConfigTargets` when the local binary or wrapper changes.
- Adding an agent must not alter existing agents' configuration except shared generated indexes when necessary.

## CLI Dispatcher

Globally installed lightweight binary containing only local-vs-global resolution logic.

**Fields**:

- `dispatcherVersion`: Version of the globally installed dispatcher package
- `resolvedTarget`: `local` or `global`
- `localBinaryPath`: Absolute path to `.spec-n-roll/cli/bin/spec-n-roll` when `local`
- `forceGlobal`: Whether `--global` bypasses local resolution

**Validation**:

- Walks parent directories from `cwd` to find the nearest `.spec-n-roll/cli/bin/spec-n-roll`.
- Exec's the resolved full CLI as a child process — MUST NOT load full CLI/core/MCP in-process when dispatching local.
- Forwards `-v`/`--version` unchanged to the full CLI binary.
- If local binary is found but exec fails, fails with clear error — no silent fallback to global unless `--global`.
- When no local binary exists and `--global` is absent, exec's co-bundled global full CLI relative to dispatcher install path.

## Full CLI

Project-local (or global fallback) binary with argument parsing, subcommands, Ink UI, and update/config operations.

**Fields**:

- `binaryVersion`: Version of the executed full CLI binary
- `invocationMode`: `interactive` (bare `spec-n-roll` → Ink) or `non-interactive` (`spec-n-roll <subcommand> [args]` → sync exit)
- `invocationContext`: `dispatcher`, `direct`, or `local-exec`
- `dispatcherVersion`: Dispatcher version when invoked via dispatcher (nullable on direct invocation)

**Validation**:

- Installed at `.spec-n-roll/cli/bin/spec-n-roll` (+ `.cmd` on Windows) when project-local.
- Bare invocation spawns Ink; subcommand invocation runs synchronously and exits.
- Shares `src/core/` with MCP server — no duplicated mutation logic.
- `-v`/`--version` prints combined report when invoked via dispatcher; direct invocation reports binary version and indicates direct invocation.

## MCP Server

Project-local stdio MCP server binary — never the global dispatcher.

**Fields**:

- `binaryPath`: `.spec-n-roll/cli/bin/spec-n-roll-mcp` (+ `.cmd` on Windows)
- `transport`: `stdio`
- `toolkitVersion`: Must match local full CLI binary version
- `registeredAt`: Timestamp when MCP config was last written for an agent

**Validation**:

- MUST NOT be invoked via global dispatcher or full CLI binary.
- Referenced from each configured agent's project-local MCP config file(s), written by `init` / `config add-agent` and refreshed by `update`.
- Version skew with full CLI surfaces as error with remediation (re-run update or init).
- Each MCP tool maps to a core-library operation with a matching non-interactive CLI subcommand.

## Core Library

Shared local library implementing all deterministic mutations invoked by MCP server and full CLI.

**Operations** (each exposed as MCP tool + CLI subcommand):

- Workflow state transitions (`workflow-state.json`)
- Task spec lifecycle status updates (`spec.md` YAML frontmatter)
- Project metadata updates (`project-metadata.json`)
- Task checkbox toggles (`tasks.md`)
- Step output template instantiation (copy template → task spec directory)
- Frontmatter field updates after instantiation

**Validation**:

- Sole writer for machine-readable state listed above.
- Living spec `.feature` files are outside core library scope — agent-managed only.
- Agents MUST NOT be instructed to directly edit machine-readable fields.

## Toolkit Version

Represents the versioned toolkit distribution installed into a project.

**Fields**:

- `version`: Semver release identifier
- `installedAt`: Timestamp of project initialization or last update
- `ownedDirectories`: Directories classified as toolkit-owned
- `userDirectories`: Directories classified as user-owned
- `compatibilityDeclarations`: Known incompatible toolkit/extension combinations

**Validation**:

- `version` must be valid semver.
- Toolkit-owned and user-owned directories must not overlap.
- Toolkit-authored documentation lives in the repository root `docs/` directory only; it is not installed into user projects and is excluded from project ownership classification.

## File Ownership Class

Classifies files by directory location.

**Fields**:

- `directory`: Project-relative directory path
- `owner`: `toolkit` or `user`
- `updateBehavior`: `overwrite-with-backup` for toolkit-owned, `preserve` for user-owned

**Validation**:

- No file-level overrides.
- Before overwriting a modified toolkit-owned file, the CLI writes a `.bak` sibling and reports it.
- User-owned files are preserved byte-for-byte unless an explicit config migration is confirmed.

## Config Schema

Represents versioned project configuration.

**Fields**:

- `schemaVersion`: Current schema version for the config file
- `workflows`: Named workflow tier variants (each lists shared `specify` as step 1 + tail)
- `steps`: Reusable step definitions
- `agents`: Agent configurations
- `extensions`: Registered extension references
- `defaultWorkflowId`: Tier pre-selected in manual/override picker only

**Validation**:

- Runtime commands may assume the current schema version.
- The CLI update path uses a tolerant reader for prior schemas, migrates, and writes the current schema.
- Breaking schema migrations require a migration plan and explicit confirmation.
- `defaultWorkflowId` does not auto-run a workflow before `specify`.

## Workflow Variant

An ordered workflow tier definition; each variant lists a shared `specify` step reference as step 1 plus a tier-specific tail.

**Fields**:

- `id`: Unique workflow variant identifier (`papercut`, `quick`, `full`)
- `name`: Human-readable name
- `description`: Purpose and intended complexity tier
- `steps`: Ordered references to reusable workflow steps (always starts with shared `specify`)
- `default`: Whether this tier is pre-selected in the manual picker (`defaultWorkflowId`)

**Validation**:

- Initialization must write papercut, quick, and full variants.
- Multiple variants reference the same `specify`, `tasks`, `plan`, and `implement` step definitions.
- Triage within `specify` selects which variant tail executes after `specify` completes.

## Workflow Step

A single executable workflow unit identified by an open kebab-case `stepId`.

**Fields**:

- `id`: Step identifier (`stepId`), e.g. `specify`, `clarify`, `plan`, `tasks`, `implement`, or custom extension-defined IDs
- `kind`: `built-in`, `extension`, or `hook`
- `command`: Agent command exposed to the developer
- `implementation`: Built-in handler or extension reference
- `priority`: Ordering when multiple extensions target the same `stepId`
- `enabled`: Whether the step can be selected
- `outputs`: Expected artifact paths (for partial-artifact detection)

**Validation**:

- Agent-facing commands must use the `spec-n-` prefix.
- The schema does not close the set of valid step IDs — workflows and extensions declare them.
- `specify` embeds triage at its start (before the interview); triage is not a separate workflow step in tier definitions.
- Disabled extensions are ignored and built-in behavior is used when available.
- If multiple enabled extensions target the same `stepId`, priority determines the active handler and the developer is informed.

## Merged Step Registry

Union of step definitions from `workflow.config.json` and enabled extension manifests, used for hook validation and step resolution.

**Fields**:

- `stepIds`: All registered step identifiers (built-in, on-demand, extension-defined)
- `sources`: Map of `stepId` → originating config or extension manifest

**Validation**:

- Built at manifest/config load time from workflow config plus enabled extensions.
- Hook events `before_{stepId}` / `after_{stepId}` are validated against this registry.
- Unknown hook `stepId` values produce a warning at load/registration and are skipped at dispatch — non-blocking.

## Step Output Manifest

Built-in mapping from step ID to expected output files for interrupted-step detection.

**Fields**:

- `stepId`: Workflow step identifier
- `expectedFiles`: Project-relative paths produced by the step

**Default mappings**:

| Step ID | Expected files |
|---------|----------------|
| `specify` | `spec.md` |
| `plan` | `plan.md` |
| `tasks` | `tasks.md` |
| `implement` | (living spec updates + test artifacts — tier-dependent; see implementation contract) |

**Validation**:

- Partial = any expected file for the current incomplete step exists while `workflow-state.json` shows that step not yet completed.
- One interrupted-step prompt covers all partial files for the step.
- Tier-skipped steps have no expected files for that task spec.

## Extension

Registered package or module that contributes steps, hooks, workflow variants, and/or agent setup (for agent-type extensions).

**Fields**:

- `id`: Unique extension identifier
- `manifestVersion`: Extension manifest schema version
- `targetToolkitVersion`: Toolkit version the extension was designed for
- `steps`: Step contributions, each with `stepId` (open string), `command`, `entrypoint`, optional `priority`
- `hooks`: Hook contributions with `event` matching `before_{stepId}` or `after_{stepId}`
- `workflowVariants`: Optional workflow variants referencing registered step IDs
- `agentSetup`: Optional agent integration block (required for bundled agent extensions) with `mcpConfig.targets`, `mcpConfig.serverId`, `mcpConfig.format`, plus `ruleTargets` and `skillTargets`

**Validation**:

- Bundled agent extensions MUST include `agentSetup.mcpConfig` with at least one target path and a stable `serverId`.
- Extension manifest `steps` use `stepId` (not `phase`) — a kebab-case string referencing the workflow slot replaced or augmented.
- Hook `event` values must match `^(before|after)_[a-z0-9][a-z0-9-]*$`; no CLI lifecycle hooks (`before_update`/`after_update`).
- Unknown hook `stepId` at load: warn and skip dispatch (non-blocking).
- Handlers are invoked in-process via Node `import()`.
- Compatibility mismatches are reported as update-time warnings.
- Warnings do not block the update or runtime startup.
- If an extension later fails at runtime after a warning, the step fails with remediation guidance.
- Toolkit upgrade integration for extensions uses CLI commands, not hook events.

## Task Spec

Directory-scoped artifact set for a single workflow run.

**Fields**:

- `taskSpecId`: Unique zero-padded numeric identifier (e.g. `001`)
- `slug`: Required kebab-case slug (developer-provided or derived from feature description)
- `path`: `specs/{taskSpecId}-{slug}/`
- `status`: `Active`, `Complete`, or `Locked` — persisted in `spec.md` YAML frontmatter
- `artifacts`: Minimum `spec.md` + `workflow-state.json`; tier-applicable `plan.md`, `tasks.md`

**Validation**:

- Numeric IDs assigned from `project-metadata.nextTaskSpecId`.
- Slugs are not required to be unique.
- Locked task specs are immutable.
- `/spec-n-specify` does not lock prior specs.
- Starting a non-specify step locks eligible Complete specs (updates their `spec.md` frontmatter to `Locked`).
- Tier-skipped artifacts are omitted — not created as stubs.

## Workflow State

The persisted operational state used by `/spec-n-roll`.

**Fields**:

- `schemaVersion`: State file schema version
- `taskSpecId`: Owning numeric task spec ID
- `slug`: Required slug matching the task spec directory
- `workflowVariantId`: Active workflow tier variant (set during triage within `specify`)
- `lastCompletedStepId`: Last successful step, or `null`
- `currentStepId`: Step that was in progress when interrupted, when known
- `status`: `active`, `paused`, `complete` (operational — not lifecycle)
- `updatedAt`: Timestamp of last state write

**Validation**:

- State wins over artifact inference when present and parseable.
- Artifact detection respects the selected tier's step list.
- State/artifact mismatches require one confirmation before proceeding.
- Missing or unreadable state triggers tier-aware artifact detection fallback.
- Interrupted partial artifacts trigger restart/cancel/force-clean.

## Project Metadata

Project-level metadata for ID assignment and implementation routing.

**Fields**:

- `schemaVersion`: Metadata schema version
- `nextTaskSpecId`: Sequential counter for new task spec numeric IDs
- `currentTaskSpecId`: Numeric ID authoritative for implementation (nullable)
- `currentTaskSlug`: Required slug paired with `currentTaskSpecId` when set
- `implementationStartedAt`: Timestamp set when implementation begins
- `updatedAt`: Timestamp of last metadata write

**Validation**:

- `nextTaskSpecId` increments atomically when a new task spec directory is created.
- Implementation fields validated and set when the implement step begins.
- Only one Active task spec may be in implementation at a time.
- `/spec-n-roll` uses this metadata at implement time.

## Step Output Template

Toolkit-owned template file for a workflow step's output artifact.

**Fields**:

- `stepId`: Workflow step the template serves (e.g. `specify` → `spec.md`)
- `templatePath`: Toolkit-owned source path (e.g. `src/templates/spec.md`)
- `targetArtifact`: Filename in task spec directory (e.g. `spec.md`)
- `frontmatterArgs`: Frontmatter fields passed as instantiate command arguments

**Validation**:

- Instantiated via MCP/CLI copy command into task spec directory.
- Templates contain inline fill instructions for each section.
- Agent skills document instantiate command and prose-editing workflow — not duplicate template structure.
- Prose content is agent-edited after instantiation; frontmatter updates use MCP/CLI only.

## Living Specification

Cucumber Gherkin `.feature` file representing current accepted behavior. Fully agent-managed — no MCP/CLI template instantiation.

**Fields**:

- `path`: `living-specs/{kebab-case-domain}.feature`
- `domain`: Capability or domain area (kebab-case)
- `scenarios`: Current Gherkin scenarios
- `taskTags`: Additive `@spec-n-roll-{numeric-id}` tags on new or modified scenarios

**Validation**:

- Agent infers domain semantically from feature description.
- Creates and updates are agent-direct — outside MCP/CLI deterministic mutation boundary.
- Planned living-spec changes documented in `plan.md`/`tasks.md` before implementation writes.
- Deprecated scenarios are removed, not archived in-repo.
- New or modified scenarios receive the current task tag.
- Existing task tags are preserved.
- Cucumber runs directly against living spec files.

## Specification Interview

Interactive specify/clarify session following grill-me guidance.

**Fields**:

- `sessionType`: `specify` or `clarify`
- `taskSpecId`: Associated numeric task spec ID
- `slug`: Associated slug
- `resolvedQuestions`: Recorded decisions
- `pendingAmbiguities`: Ranked unresolved ambiguities
- `recommendedAnswer`: Suggested answer for the current question
- `triageResult`: Selected workflow tier variant (specify sessions only, before interview)

**Validation**:

- Specify sessions run triage before the interview and persist `workflowVariantId`.
- Ask exactly one targeted question at a time.
- Explore the repository instead of asking questions that can be answered from code.
- Do not re-ask resolved questions.
- End only when critical ambiguities are resolved and the developer is satisfied.

## TDD Cycle

One vertical red-green-refactor slice for implementation.

**Fields**:

- `behavior`: Observable behavior under test
- `publicInterface`: CLI command, workflow command, config contract, or living spec behavior
- `redResult`: Expected failing test evidence
- `greenResult`: Passing result after minimal implementation
- `refactorResult`: Passing result after cleanup

**Validation**:

- Tests describe behavior, not implementation.
- One behavior is tested per cycle.
- Never refactor while red.
- Do not add speculative code for future tests.
